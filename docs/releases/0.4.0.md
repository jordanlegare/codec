# CODEC 0.4.0 — Compressed Media Preservation

Released: 2026-09-01

## Program description

**CODEC is a C++20 preservation-first stream capture and archival engine that records exact source bytes into append-only CODA archives, validates integrity and provenance, and preserves compatible H.264/AAC media as compressed packet state for direct MP4 remux instead of storing decoded video frames or PCM audio.**

The command-line program supports concurrent local, standard-input, HTTP, and HTTPS capture; archive verification and inspection; source-exact extraction; verified-prefix follow extraction while an archive is growing; non-mutating repair; explicit FFmpeg-backed video ingest; and verified MP4 export. The installed C++ library additionally exposes generic stream/provenance, audio-profile, transport/recovery, and bounded distributed-processing primitives.

CODEC is preservation-first rather than a general media transcoder. It keeps accepted source representations as S0, profile-defined exact state as S1, and derived/inferred artifacts as D with provenance. It does not claim that archive hashes authenticate an external identity, and it does not silently turn unsupported media into a different representation.

## Why 0.4.0 is a major 0.x release

0.4.0 is the first release that packages the Stage H.1 Video Stream Profile as a coherent compressed-media workflow rather than an experimental raw-frame persistence path.

Before this release, new H.1 FFmpeg ingest could preserve exact source/container bytes and then duplicate video as per-frame decoded `VFR1` pixel payloads. At YUV420P8, one decoded frame requires roughly 1.5 bytes per pixel before record/provenance overhead, so even a short high-resolution capture could dwarf the original compressed media. Earlier audiovisual work also persisted aggregate PCM16 audio before EAP1 packet preservation replaced it.

In 0.4.0, new compatible audiovisual ingest preserves:

```text
accepted source/container or HLS resources  -> S0
selected H.264 compressed packets           -> EVP1 / 0x0104 / S1
selected AAC compressed packets             -> EAP1 / 0x0103 / S1
```

Video and audio are still decoded incrementally during ingest to validate the selected stream, timing, geometry, and resource bounds. The decoded buffers are then discarded. New H.1 ingest does **not** persist per-frame VFR1 pixels or Video Profile PCM16 state.

This does not mean CODEC stores “MP4 compression.” MP4 is a container. CODEC preserves the compatible compressed elementary-stream packets inside the source—currently H.264/AVC video and AAC audio for the H.1 packet-preservation path—and can regenerate an MP4 container by remuxing those verified packets.

## Release highlights

### EVP1 compressed H.264 state

`EVP1` is the versioned encoded-video S1 representation registered under profile-local record code `0x0104`.

It preserves the selected H.264 stream's compressed packet payloads plus the bounded metadata needed to verify and remux them, including codec/framing information, decoder configuration when available, dimensions, PTS/DTS timing, durations, flags, and presentation evidence. H.264 presentation reordering is supported: PTS may differ from monotonic decode order/DTS.

Direct MP4/media ingest binds EVP1 to the exact same-stream S0 source object. Same-origin unencrypted HLS binds EVP1 to the primary manifest plus the accepted child-resource frontier captured through CODEC.

### EAP1 compressed AAC state

`EAP1` remains the encoded-audio S1 representation under record code `0x0103`.

Compatible AAC packet payloads are retained instead of accumulating decoded PCM16. Audio decoding is validation-only. Decoder configuration, timing, presentation-frame counts, packet data, and trim metadata are validated under bounded resource limits.

The legacy Video Profile PCM16 state `0x0102` remains readable/exportable but is no longer written by new compatible audiovisual ingest.

### MP4 export is packet remux when compatible

For new H.1 archives, verified MP4 export prefers:

```text
EVP1 H.264 packets + EAP1 AAC packets
                 |
                 v
              MP4 mux
```

No H.264 encoder or AAC encoder is used on the compatible packet-preservation path.

H.264 configuration handling is explicit:

- length-prefixed AVC requires valid decoder configuration;
- Annex-B H.264 can use FFmpeg `extract_extradata` to recover in-band SPS/PPS;
- if required configuration cannot be recovered safely, export fails with `model_incompatible` instead of transcoding silently.

AAC configuration handling is explicit:

- AAC with stored MPEG-4 AudioSpecificConfig is packet-copied into MP4;
- ADTS AAC with no global decoder configuration uses FFmpeg `aac_adtstoasc` to derive AudioSpecificConfig and remove ADTS headers without decoding/re-encoding audio;
- unsupported or contradictory retained packet semantics fail closed.

### AAC leading trim / preroll

0.4.0 includes the leading-trim fix merged after the initial compressed-video work.

Valid AAC may begin before the selected video presentation origin. EAP1 represents that with `trim_start_frames` plus negative compressed packet PTS/DTS. MP4 can represent this legitimate preroll through edit-list timing.

The 0.4.0 exporter therefore:

- keeps representable negative AAC preroll timestamps;
- enables MP4 edit-list timing for non-zero leading trim;
- keeps stored-ASC AAC in the compressed packet domain;
- keeps ADTS-to-ASC AAC in the compressed packet domain;
- rejects a contradictory state that claims leading trim but contains no negative compressed preroll evidence.

This fixes extraction failures of the form:

```text
model_incompatible: encoded AAC leading trim cannot be represented by H.1 MP4 passthrough
```

when the archived state actually contains valid representable preroll.

## H.1 record compatibility

| Record | Code | 0.4.0 role |
|---|---:|---|
| `VPD1` descriptor | `0x0100` | Video profile descriptor metadata. |
| `VFR1` raw video frame | `0x0101` | Legacy/read-export compatibility. New compatible FFmpeg audiovisual ingest does not write per-frame VFR1 pixels. |
| Video PCM16 audio | `0x0102` | Legacy/read-export compatibility. New compatible audiovisual ingest does not write this state. |
| `EAP1` encoded AAC | `0x0103` | Current compressed-audio S1 state. |
| `EVP1` encoded H.264 | `0x0104` | Current compressed-video S1 state. |

Existing CODA archives containing valid `0x0101` or `0x0102` records remain readable and exportable through compatibility paths. 0.4.0 does not rewrite an existing archive in place.

An archive that presents contradictory verified forms for the same H.1 stream—for example both EVP1 and VFR1, or both EAP1 and Video PCM16—fails closed rather than guessing which representation is authoritative.

## Source preservation and HLS boundaries

### Direct file / HTTP / HTTPS media

The accepted source snapshot is committed as exact S0 before profile interpretation. FFmpeg demux/decode operates on the captured bytes through CODEC-owned I/O rather than gaining independent network authority for direct media.

### HLS

0.4.0 supports bounded **same-origin unencrypted HTTP/HTTPS HLS** in the H.1 ingest bridge.

CODEC captures the primary manifest and every accepted child object as exact S0 before those bytes are supplied to FFmpeg. Child resources are authorized by CODEC's capture policy. The profile rejects encryption/key retrieval, cross-origin children, private-network-denied children, malformed/non-HTTP(S) requests, and native FFmpeg protocol fallback outside the authorized boundary.

DASH, encrypted HLS, arbitrary FFmpeg protocol access, browser-cookie/session emulation, and general-purpose network playback are not implemented.

## CLI version and release identity

All runtime release identity is derived from CMake `PROJECT_VERSION`.

For 0.4.0:

```bash
codec --version
```

returns:

```text
codec 0.4.0
```

The help banner begins with `CODEC 0.4.0`, and:

```bash
codec capabilities
```

reports:

```json
{"version":"0.4.0", ...}
```

The capabilities object remains a small runtime declaration. It does not currently add separate H.1/FFmpeg capability keys; FFmpeg backend availability is exposed through the C++ Video Profile API.

## CLI examples

### Preserve one video source

```bash
codec video ingest \
  --source ./camera.mp4 \
  --archive camera.coda \
  --label camera \
  --start-ns 0 \
  --end-ns 10000000000
```

`--layout` remains accepted for H.1 compatibility, but new EVP1 storage is compressed-packet based and is not changed by choosing `gray8`, `rgb24`, `rgba32`, or `yuv420p8`.

### Preserve multiple video sources into one archive

```bash
codec video ingest --archive cameras.coda \
  --video --source ./left.mp4  --label left  --start-ns 0 --end-ns 10000000000 \
  --video --source ./right.mp4 --label right --start-ns 0 --end-ns 10000000000
```

Each `--video` block has its own source, label, interval, and Video Options. The archive remains one CODA file containing the separate logical video streams and their exact source/provenance records.

### Export one verified stream

```bash
codec video export camera.coda \
  --stream <UUID> \
  --output camera.mp4
```

### Export every video stream

```bash
codec video export cameras.coda \
  --all \
  --output-dir extracted
```

Compatible EVP1/EAP1 streams are remuxed. Legacy VFR1/PCM16 states use their compatibility export paths.

## Storage expectations

0.4.0 intentionally makes no universal archive-reduction factor claim because the result depends on source codec, bitrate, resolution, frame rate, audio bitrate, HLS segmentation, and exact S0 duplication.

The structural change is deterministic: new compatible H.1 ingest no longer adds one raw decoded pixel record per video frame and no longer adds aggregate Video Profile PCM16 audio. Archive size therefore tracks:

1. exact accepted S0 source/container or HLS objects;
2. a bounded compressed EVP1 copy of selected H.264 packets;
3. a bounded compressed EAP1 copy of selected AAC packets;
4. CODA record/provenance/index overhead.

For audio only, 48 kHz stereo PCM16 is 192,000 bytes/s (691.2 MB/hour), while a 128 kbit/s compressed stream is 16,000 bytes/s (57.6 MB/hour) before packet-table and archive overhead—about twelve times smaller for that specific workload.

A later optimization could reference packet byte ranges inside S0 instead of duplicating compressed payloads into EVP1/EAP1, but 0.4.0 deliberately does not introduce that additional container/segmentation complexity.

## Build requirements

Default 0.4.0 builds enable the FFmpeg Video Profile bridge and require development packages for:

- `libavformat`
- `libavcodec`
- `libavutil`
- `libswscale`
- `libswresample`

The media-library-independent H.1 schemas/readers remain available with:

```bash
cmake -S . -B build-no-ffmpeg \
  -DCODEC_ENABLE_FFMPEG_VIDEO=OFF
```

The project continues to require CMake 3.20+, C++20, OpenSSL 3 Crypto, libcurl, pkg-config, and libFLAC for the normal package.

## Failure semantics

0.4.0 keeps H.1 fail-closed:

- source capture can succeed even if later profile interpretation fails; accepted S0 remains preserved;
- malformed or unsupported encoded state is not mislabeled as valid S1;
- missing/recoverable packet configuration is handled only by explicit validated recovery paths;
- unrecoverable packet configuration returns `model_incompatible` rather than silently re-encoding;
- contradictory verified state forms return archive/profile errors;
- output/resource limits return explicit bounded failures;
- MP4 export does not re-fetch the original source.

## What 0.4.0 does not claim

0.4.0 is not a general-purpose video transcoder or playback framework. It does not provide:

- arbitrary video/audio codec preservation/remux beyond the implemented H.264/AAC H.1 path;
- DASH;
- encrypted or cross-origin HLS;
- GPU decode or video inference;
- bundled production neural models;
- GStreamer integration;
- a distributed-processing CLI or concrete remote-worker network service;
- cryptographic authentication of stream identity from archive hashes;
- production-scale throughput, latency, availability, durability, or storage-ratio guarantees;
- Stage G trust/selective-disclosure completion;
- H.2+ profile stages.

## Upgrade guidance from 0.3.0

1. Rebuild against 0.4.0 so `PROJECT_VERSION`, the installed CMake package, shared-library version metadata, CLI `--version`, help banner, and capabilities report the same release.
2. Existing 0.3.0 CODA archives remain inputs; there is no required archive migration step.
3. New H.1 video ingest produces EVP1/EAP1 rather than VFR1/Video-PCM16 for compatible H.264/AAC media.
4. Scripts should not infer stored video-frame count from the CLI JSON `frames` field as a raw-pixel record count for new EVP1 archives; the H.1 state model is interval packet state rather than per-frame persistence.
5. `--layout` is retained for compatibility but does not change the bytes stored in new EVP1 state.
6. If an export fails with `model_incompatible`, inspect the message. 0.4.0 distinguishes recoverable Annex-B/ADTS configuration and representable AAC preroll from genuinely unrepresentable compressed state.

## Release verification contract

The release-preparation branch must pass the repository's full CI matrix on the exact head SHA:

- GCC configure/build/tests/install/package consumer;
- Clang configure/build/tests/install/package consumer;
- sanitizers;
- FFmpeg-disabled build/tests/install/package consumer;
- CLI integration, including `--version`, help-banner version, and capabilities version;
- repository AI contract/version continuity.

Publication uses the existing `release/v*` workflow. The release branch must point at the exact same commit as `main`, contain `project(CODEC VERSION 0.4.0 ...)`, contain README machine-readable `version: 0.4.0`, and contain a `## 0.4.0 — ...` changelog section. The workflow then creates tag `v0.4.0` and GitHub release `CODEC v0.4.0` from that changelog section.
